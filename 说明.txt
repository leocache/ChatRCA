完整升级版的核心思想不是简单“把模型换新”，而是把整套系统从“自由讨论式分析”升级成“结构化协作式诊断”。升级后的目标是：无论是 TrainTicket 还是 GAIA，程序最终都必须输出一个统一 JSON，其中至少包含 root_cause_category、root_cause_detail、service_location、affected_service、confidence、evidence 和 expert_findings。这里的 root_cause_category 用来表示根因类别，比如 network、resource、application、database、middleware、dependency、configuration 或 unknown；service_location 用来表示服务定位信息，它不是单一字段，而是一组层级化字段，允许你定位到 service、pod、container、node、ip、trace_service、trace_span 中的任意粒度。这样做的意义在于，真实数据里有时只能定位到 service，有时可以直接命中 pod 或 node，有时 trace 里甚至可以落到某个 span，如果你只设计一个 service 字段，会把这些更精细的定位能力浪费掉。

完整版本中，工程可以理解为由五层构成。第一层是数据入口层，也就是 main.py 和 utils/__init__.py 配合 read_file.py 读入故障描述与原始数据。你现在的 __init__.py 已经封装了 get_fault_info()，它会根据数据集名找到故障目录，再读取故障描述和目录里的 csv 文件。main.py 里则分别为 TrainTicket 和 GAIA 组织故障上下文，并启动群聊。 第二层是观测与预处理层，主要由 skills4tt.py、skills4gy.py、filter_tools.py、csv2md.py 组成，它们负责把 csv 数据读出来，转成 markdown 字符串，并在日志、指标、链路数据上做初筛。这里原本就有 process_log_data()、process_metric_data()、process_trace_data() 这些函数，但旧版返回的只是原始或简单过滤后的文本，缺少“结构化异常摘要”。 第三层是定位增强层，这是升级版新增的，包括 schemas.py、utils/location_tools.py 和 utils/observation_summary.py。schemas.py 定义统一输出协议，location_tools.py 负责把故障描述里的 service、pod 等信息规整成标准位置对象，比如把 TrainTicket 里的 pod 名去掉后缀还原出服务名，或者为 GAIA 构造 suspected service location；observation_summary.py 则把原始日志、指标、trace 提炼成适合推理的异常摘要，让专家不再直接对大块文本盲猜，而是基于“异常字段 + 异常值 + 可能服务位置”的证据做判断。第四层是多专家推理层，也就是升级后的 agents.py。这里最大的变化是每个专家不再自由输出段落式意见，而是必须输出 JSON，只能围绕四件事回答：根因类别是什么、服务位置在哪里、证据是什么、置信度多少。总控运维代理不再只是“写报告的人”，而是“诊断裁决器”，负责收集其它专家 JSON，比较证据强弱和置信度，生成最终 FinalDiagnosis。第五层是结果消费层，也就是升级后的 main.py 在群聊结束后自动从回复中提取 JSON，解析后打印、保存，或者继续送去后续评估与统计。

你如果要真正把完整版本落地，目录建议保持和你当前工程一致，只是在现有基础上补几个文件。最小可工作的完整版本结构可以是：根目录保留 main.py、agents.py、__init__.py，在 utils/ 下保留现在的 csv2md.py、filter_tools.py、read_file.py、skills4tt.py、skills4gy.py，再新增 location_tools.py 和 observation_summary.py，同时在根目录新增 schemas.py。其中 schemas.py 负责定义 ServiceLocation、EvidenceItem、ExpertFinding、FinalDiagnosis 这些统一数据模型；location_tools.py 负责诸如 infer_service_from_pod()、normalize_trainticket_pod_to_service()、build_observation_ticket() 之类函数；observation_summary.py 负责把 process_log_data()、process_metric_data()、process_trace_data() 的原始结果进一步包装成 {"raw": ..., "summary": ...} 的格式。这样一来，整个观测链路从过去的“只给原始文本”变成“同时给原始文本和摘要证据”，专家看到的数据就会稳定很多。

完整版本里每个核心文件的职责也需要明确下来。main.py 的职责应该是“读入故障、构建 incident context、发起群聊、解析最终 JSON”，而不是在这里写诊断逻辑。旧版 main.py 已经能区分 TrainTicket 和 GAIA，分别从 fault.txt 或 groundtruth.txt 中提取时间和服务信息，这是可以保留的，但要把发给群聊的 message 从过去那种一句话描述，改成一个带结构上下文的 incident message，例如包含 incident_id、dataset、fault_time 或 fault_start_time/fault_end_time、fault_message、suspected_service_location，同时在提示词里明确要求“return final JSON only”。 agents.py 的职责则是声明所有代理、设定系统提示词、注册观测工具并组装 GroupChat。旧版这里已经有 OperationEngineer、ArchitectExpert、ResourceExpert、NetWorkExpert、Observable_engineer_agent 和 Operator，说明你原始的角色划分是够用的，不需要重做；真正要改的是它们的 system message，要把“结构化产出”写死，并把 human_input_mode 从很多地方的 ALWAYS 改成稳定自动化运行时更适合的 NEVER，否则每次跑都会卡在人机介入上。 filter_tools.py 的职责是异常筛选逻辑，这里建议保留你现有三个函数，但要修一个关键错误：当前 filter_metric_data() 的注释写的是 NodeCpuUsageRate 高于阈值视为异常，代码却写成了 node_cpu_usage < cpu_usage_threshold，这会把许多高 CPU 负载样本漏掉或反向筛选。 read_file.py 的职责是目录遍历与基础文件读取，这里也建议修一下 read_md_files_from_directory() 的路径拼接方式，因为它通过 glob 拿到的是完整路径，但又把这个完整路径作为“文件名”传给 read_md_files_in_name(directory, file) 做二次拼接，容易产生错误路径。 skills4tt.py 和 skills4gy.py 的职责是根据数据集暴露统一技能给 AutoGen 调用，这里你要重点统一返回格式，因为旧版 TrainTicket 的 process_metric_data() 返回字符串，而 GAIA 的 process_metric_data() 返回字典，两边不一致，升级后最好都返回 {"raw": ..., "summary": ...}。

完整版本的执行流程是这样的。程序启动后，main.py 先通过 get_fault_info() 拿到故障描述和数据目录。对于 TrainTicket，它会从 fault.txt 里取出 inject_time 和 inject_pod，并通过去两次后缀的方式把 pod 规整成服务名；对于 GAIA，它会取出 date、service、message、st_time、ed_time 等信息。然后 main.py 调用 build_observation_ticket() 形成一个统一 incident context，这一步的意义是，不管底层数据集长什么样，发给群聊的故障上下文都长成一致的结构。接着 User_proxy 发起群聊，Observable_engineer_agent 按需调用 data、architecture_information、log_data_processing、metric_data_processing、trace_data_processing 这些已注册函数，从本地读取相关数据并返回观测证据。旧版这些函数在 agents.py 里已经通过 register_function() 绑定给了 Observation Agent，只是以前只是返回原始文本。 升级版里，Observation Agent 从工具拿到的应当是原始数据加摘要数据，然后把这些证据提供给网络专家、资源专家和架构专家。网络专家重点判断超时、连接错误、通信链路异常、DNS 或路由问题，并尽量在 service_location 里给出 service、pod、ip 或 trace_service；资源专家重点判断 CPU、内存、节点资源、容器资源、运行时瓶颈，并尽量给出 pod、container、node；架构专家重点根据服务依赖和部署关系补充 service 拓扑位置。每个专家的输出都必须是合法 JSON，里面至少要带 root_cause_category、service_location、summary、confidence、evidence。等这些专家意见收集到足够多以后，OperationEngineer 作为最终裁决器比较各方结论，把置信度最高、证据最强的诊断作为最终答案，输出一个完整的 FinalDiagnosis JSON。main.py 最后用正则从最终文本中提取 JSON，并 json.loads() 成 Python 对象，再打印或写文件。

你问“使用说明”，如果按运行者视角来讲，完整版本的使用方式其实很直接。你先准备好数据目录和配置。你的代码现在已经依赖 config.yaml 来决定 fault 路径，read_file.py 里 get_fault_path() 会去 config.yaml 里读取 fault 这个键，然后拼接成数据集目录下的故障样本路径，所以你要先保证根目录存在对应数据集目录，比如 TrainTicket/ 或 GAIA/，并且里面的故障目录结构符合当前读取逻辑。 对 TrainTicket，故障目录中至少要有 fault.txt、log.csv、metric.csv、trace.csv；对 GAIA，至少要有 groundtruth.txt、filtered_log.csv、filtered_trace.csv 和 metric/ 目录。当前 skills4tt.py 和 skills4gy.py 已经写死了这些文件名，所以目录名最好保持一致。 然后你要在环境变量里配置 OPENAI_API_KEY，因为 agents.py 里 config_list 是直接从 os.environ.get("OPENAI_API_KEY") 取值。 之后执行 python main.py 即可，默认跑哪一个数据集由 if __name__ == "__main__" 下面调用哪个函数决定。旧版是默认 run_GAIA_fault()，升级版也可以继续这么做，只是换成新的结构化 run_fault() 或新的 run_GAIA_fault()。 当程序执行后，你在终端上应该能看到最终打印出的 JSON 诊断结果，里面会明确显示根因类别和服务位置，而不再只是泛泛一段自然语言报告。

从开发者维护视角讲，完整版本最重要的使用原则是：以后你新增专家或新增数据处理逻辑，都要遵守统一 schema。比如你以后想再加一个 DatabaseExpert，完全可以加，但它的输出也必须是 ExpertFinding 这个结构，而不是自己写一段说明文；如果以后你想让 trace 里多提取 service_path，也建议作为 service_location 的补充字段或另一个结构化字段输出，而不是埋在长段落里。这样整个系统才可评估、可统计、可调试。否则一旦重新回到自由文本，main.py 就很难稳定解析。
